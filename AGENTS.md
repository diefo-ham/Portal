# Project principles

- Offline-first, private study on one laptop. Essential workflows must need no internet after installation.
- User-imported question material is data, never repository content. Commit only original synthetic examples. Never scrape or bypass a test publisher's controls.
- The app ships one set of original example questions per test (SAT, PAA, TSI) in `public/examples/`, written for the portal (not a test publisher's items), marked `bundled`, with no active/inactive status. They study like any other question but are not the person's own: they never unlock the Tests screens (Practice Tests, Test mode, Tests, locked until the person imports questions of their own for that test), are never used to build a test, and "Remove my questions" leaves them. Once a test has imported questions, its examples are hidden by default (the TSI keeps showing them by default) and a Study-preferences switch (offered only then) changes it. An imported question replaces an example with the same source ID. The portal is the same for everyone; there is no edition switch. See `docs/examples.md`.
- Hide active practice-test questions by default. Unknown is explicit and is not a promise that a question is safe from spoilers. The protection controls (the "Protect unused practice-test questions" setting and the active filter) exist only once the person has imported questions.
- The question is central. Prefer study usefulness, calm typography, and accessible interaction over gamification or dashboards.
- Notes are intentionally absent from the product; retain the legacy note field only for stored-data/backup compatibility. Bookmarks remain useful, and progress reset preserves them unless the user explicitly chooses to clear them.
- Keep presentation highly iterable. Core question rules, import normalization, persistence, calculator providers, and analytics must remain separate from UI.
- The calculator is the locally bundled Offline engine and makes no external requests. The hosted comparison calculator was retired on 2026-11-03; the comparison scripts under `scripts/` use its API key only on a developer's own machine, never in the app, the build or CI. Never commit an API key.
- The portal serves three tests, SAT, PAA and TSI, from one codebase. `assessment` is a first-class field on questions, attempts and sessions; stored data without it is SAT. Study screens get a view scoped to one test, progress and bookmarks never mix, and PAA and TSI internal IDs start with `paa-` and `tsi-` so they can never collide with an SAT ID or each other. Test differences live in `src/core/assessments.ts`, not in the UI. TSI items are labelled Official (a publisher's sample) or Original, the Original ones can be switched off in Settings without deleting anything or ending a session, and a build can leave the Official ones out; the TSI has no clock and shows no score. See `docs/paa.md` and `docs/tsi.md`.
- Prefer maintainable, small solutions over enterprise complexity. Preserve progress and working behavior during redesigns.
- Import takes one PDF per test (SAT, PAA, TSI), any file names, sorted by the Assessment column. Each PDF must carry that test's access code (`Ref. …`, bottom left; finding it on any one page accepts the whole PDF); the SAT reads its ACTIVE / INACTIVE badge. The app keeps the code's hash with the questions it read, and the accepted hashes live in `src/core/accessCodes.ts`: when the app loads it removes the questions of any PDF whose code is no longer accepted (answers and bookmarks stay), and a new version is installed through an update pop-up that cannot be dismissed. Commit only SHA-256 hashes of codes, never the codes, and never a real PDF that carries one. The check is a deterrent, not copy protection. See `docs/pdf-import.md`.
- Validate imports as untrusted data. Do not execute imported HTML or fetch remote question assets.
- Run meaningful core and workflow tests before stable checkpoints. Never commit real exports, backups, or browser profiles.
